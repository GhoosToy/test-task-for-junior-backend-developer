# Task Service

Сервис для управления задачами с HTTP API на Go. Поддерживает как обычные, так и периодические задачи.

## Требования

- Go 1.23+
- Docker и Docker Compose
- PostgreSQL 16+

## Быстрый запуск

` ` `bash
docker compose up --build
` ` `

Сервис будет доступен: http://localhost:8080

Если менялась схема БД:

` ` `bash
docker compose down -v
docker compose up --build
` ` `

## Swagger документация

- UI: http://localhost:8080/swagger/
- JSON: http://localhost:8080/swagger/openapi.json

## API Endpoints

### Обычные задачи

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| POST | /api/v1/tasks | Создать задачу |
| GET | /api/v1/tasks | Список задач |
| GET | /api/v1/tasks/{id} | Получить задачу |
| PUT | /api/v1/tasks/{id} | Обновить задачу |
| DELETE | /api/v1/tasks/{id} | Удалить задачу |

### Шаблоны периодических задач

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| POST | /api/v1/templates | Создать шаблон |
| GET | /api/v1/templates | Список шаблонов |
| GET | /api/v1/templates/{id} | Получить шаблон |
| PUT | /api/v1/templates/{id} | Обновить шаблон |
| DELETE | /api/v1/templates/{id} | Удалить шаблон |
| GET | /api/v1/templates/{id}/occurrences | Даты вхождений |

### Экземпляры задач

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| GET | /api/v1/tasks/recurring?date= | Задачи на дату |
| PATCH | /api/v1/instances/{id}/complete | Выполнить |
| PATCH | /api/v1/instances/{id}/skip | Пропустить |
## Типы периодичности

| Тип | Описание | Параметры |
|-----|----------|-----------|
| daily | Каждые N дней | interval, start_date |
| monthly | Определенного числа | day_of_month, start_date |
| specific | Конкретные даты | specific_dates, start_date |
| parity | Четные/нечетные дни | parity, start_date |

## Примеры запросов

### Создать шаблон (ежедневно)

` ` `bash
curl -X POST http://localhost:8080/api/v1/templates \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Утренний обход",
    "recurrence": {
      "type": "daily",
      "interval": 1,
      "start_date": "2026-04-07T00:00:00Z"
    }
  }'
` ` `

### Получить задачи на дату

` ` `bash
curl "http://localhost:8080/api/v1/tasks/recurring?date=2026-04-07"
` ` `

### Отметить выполнение

` ` `bash
curl -X PATCH http://localhost:8080/api/v1/instances/1/complete
` ` `

## Обоснование принятых решений

### 1. Архитектура: две таблицы (шаблоны + экземпляры)

**Почему не хранить всё в одной таблице?**

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| Одна таблица с полем `recurrence` | Простота | Нельзя отследить статус каждого вхождения |
| Две таблицы (template + instance) | Можно отмечать выполнение/пропуск каждого дня | Сложнее код |

**Выбрал две таблицы**, потому что врачам важно знать, выполнили они задачу сегодня или пропустили.

### 2. Хранение правил в JSONB

**Почему не отдельные колонки?**

- Отдельные колонки (`recurrence_type`, `interval`, `day_of_month`...) → много NULL полей, сложно добавлять новые типы
- JSONB → гибкость, легко добавлять новые типы периодичности (например, "каждую пятницу"), PostgreSQL умеет индексировать JSONB

### 3. Фоновая генерация экземпляров (cron)

**Почему не вычислять на лету при каждом запросе?**

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| Вычислять на лету | Нет дублирования, экономия места | Каждый запрос считает даты заново |
| Генерировать заранее | Быстрые запросы, можно хранить статусы | Нужен фоновый процесс, больше данных |

**Выбрал гибрид:** при создании шаблона ничего не генерируем, но раз в сутки worker создает экземпляры на 30 дней вперед. Баланс между производительностью и актуальностью.

### 4. Обработка граничных случаев

**31 число в феврале** → задача выполняется в последний день месяца (28 или 29). Врач не должен пропустить задачу из-за того, что в феврале нет 31 числа.

**Четные/нечетные дни** → корректно работают во всех месяцах, включая 31-дневные.

### 5. Статусы задач

| Статус | Когда используется |
|--------|-------------------|
| `new` | Задача создана, не выполнена |
| `in_progress` | Врач начал выполнять |
| `done` | Выполнена успешно |
| `skipped` | Пропущена (не требуется выполнение) |

**Почему `skipped` отдельно от `done`?** Чтобы анализировать: задачу реально выполнили или просто пропустили.

### 6. Использование clean architecture

- **Domain** не зависит от внешних слоев → бизнес-правила можно тестировать изолированно
- **UseCase** содержит только бизнес-логику
- **Repository** можно легко заменить (например, с PostgreSQL на MongoDB)
- **Transport** можно расширить (например, добавить gRPC)

### 7. Почему не использовал cron-библиотеки

В ТЗ требовались конкретные типы периодичности (daily, monthly, specific, parity). Реализовал свой генератор дат, потому что:
- Проще контролировать логику
- Легче тестировать (7 юнит-тестов)
- Нет лишних зависимостей

Если потребуется поддержка cron-выражений (например, "каждую пятницу в 10:00"), можно добавить библиотеку `github.com/robfig/cron/v3`.

### Альтернативы, которые рассматривал

1. **Использовать отдельную очередь задач (RabbitMQ/Kafka)** → избыточно для текущих требований
2. **Хранить все экземпляры сразу на 10 лет** → слишком много данных, нет смысла
3. **Использовать `time.Ticker` для проверки каждую минуту** → нагружает CPU, cron-задачи раз в день достаточно
